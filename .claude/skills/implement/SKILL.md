# 스펙 구현

프로젝트 루트의 `SPEC.md`를 구현한다. `SPEC.md`가 없으면 진행하지 말고 `/spec`으로 먼저 스펙을 만들라고 안내한다.

## 1. 구현 계획 세우기

`SPEC.md`, `CLAUDE.md`, 관련 코드를 읽고 구현 계획을 세운다. 계획에는 다음을 적는다.

- **구현 방법**: 고치거나 새로 만들 파일과 각 파일에서 할 일. 기존 구조(`storage` → `useHabitStore` → `App` → `components`)와 패턴을 따른다.
- **남길 E2E 테스트**: 아래 [E2E 테스트 고르기](#e2e-테스트-고르기) 기준으로 고른 테스트와 각 테스트가 확인하는 완료 조건. 이미 있는 테스트로 확인되는 것은 그 테스트 이름을 적는다.
- **완료 조건별 확인 방법**: AC마다 E2E 테스트, Playwright MCP로 직접 조작, 또는 둘 다 중 무엇으로 확인할지와 구체적인 확인 내용.

## 2. 계획 검토받기

Agent 툴로 `plan-reviewer` 서브에이전트를 불러 계획을 검토받는다. 프롬프트에는 계획 전문을 그대로 넣는다.

## 3. 검토 결과 반영하기

지적마다 `SPEC.md`, `CLAUDE.md`, 코드를 근거로 타당한지 직접 판단한다. 서브에이전트의 지적을 그대로 따르지 않는다.

- 타당한 지적은 계획에 반영한다.
- 반영하지 않는 지적은 이유를 남겨 두었다가 마지막 보고에 쓴다.
- `[사람 확인]` 지적이 하나라도 있으면 구현에 들어가기 전에 AskUserQuestion으로 사용자에게 물어본다. 답을 계획에 반영하고, 스펙이 바뀌는 답이면 `SPEC.md`도 고친다.
- `[사람 확인]` 지적이 없으면 사용자에게 계획을 확인받지 않고 바로 구현으로 넘어간다.

`[사람 확인]`이 붙지 않았더라도 새 npm 패키지 설치처럼 `CLAUDE.md`가 사용자에게 먼저 물어보라고 한 일은 물어본다.

## 4. 구현하고 E2E 테스트 쓰기

계획대로 구현하고 E2E 테스트를 쓴다. 구현하다가 계획과 다르게 가야 하면 이유를 남겨 마지막 보고에 쓴다.

E2E 테스트는 `CLAUDE.md`의 E2E 관례(날짜 고정, 선택자, `addHabit` 등 기존 헬퍼)를 따르고 `e2e/`의 기존 테스트와 같은 스타일로 쓴다.

### E2E 테스트 고르기

완료 조건마다 하나씩 쓰지 않는다. 앞으로 기능을 더 만들어도 깨지면 안 되는 중요한 동작만 골라서 쓴다.

- 사용자가 자주 사용하는 주요 기능이나 작업 흐름
- 다른 기능과 연결되어 있어서 변경할 때 깨지기 쉬운 동작
- 잘못된 입력을 막는 동작 중 대표적인 경우

테스트 하나로 완료 조건 여러 개를 확인해도 된다. 이미 있는 테스트로 충분히 확인되는 것은 새로 쓰지 않는다. 기존 테스트가 이번 변경으로 기대 동작이 바뀌었다면 고친다.

## 5. 완료 조건 확인하기

먼저 `npm run typecheck`, `npm run lint`, `npm run test:e2e`를 돌려 모두 통과시킨다.

그다음 완료 조건을 하나씩 확인한다. 한 조건을 여러 방법으로 확인해도 된다.

- E2E 테스트로 확인되는 조건은 해당 테스트의 통과 결과를 근거로 쓴다.
- 테스트로 확인되지 않는 부분(화면 배치, 문구, 테스트로 남기지 않은 경우 등)은 Playwright MCP로 앱을 직접 실행하고 조작해서 확인한다.
  - 개발 서버는 `npm run dev -- --port 5199 --strictPort`를 백그라운드로 띄워 쓰고, 확인이 끝나면 끈다.
  - 저장 데이터가 필요하면 `browser_evaluate`로 `localStorage`의 `oneuldo` 키를 채우거나 `?mock`으로 접속한다. 날짜가 걸린 동작은 브라우저 시계를 고정해 확인한다.
  - 화면 배치나 표시는 스크린샷이나 스냅샷으로 확인한다.

확인하다 문제를 찾으면 고치고, 고친 뒤에는 검증 명령과 영향받는 조건 확인을 다시 한다.

## 6. 보고하기

다음을 보고한다.

- **완료 조건**: AC마다 통과 여부와 확인 근거(테스트 이름, 또는 MCP로 무엇을 조작해 무엇을 봤는지). 실제로 확인하지 못한 조건은 통과로 표시하지 말고 "확인 못 함"과 이유를 쓴다.
- **검토 지적**: 반영한 지적, 반영하지 않은 지적과 그 이유, `[사람 확인]`에 대한 사용자의 답.
- **E2E 테스트**: 새로 쓰거나 고친 테스트와 각 테스트가 확인하는 완료 조건, 새로 쓰지 않은 조건은 어떤 기존 테스트나 확인으로 대신했는지.
- 구현 중 계획과 달라진 점이 있으면 함께 쓴다.

커밋은 하지 않는다. `SPEC.md`도 지우지 않고 그대로 둔다.
